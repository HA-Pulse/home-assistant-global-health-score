# HAGHS v2.4.0 Changelog

All changes on the `dev` branch after the v2.3.0 release. The fixes
previously collected in the v2.3.1 changelog are included here; v2.3.1 was
never released separately.

## Behavior changes

- **No PSI and no CPU/RAM fallback sensors (#123):** entries with both fields
  empty now raise the `fallback_missing` repair and do not set up until the
  sensors are configured; the setup gate checks the configured values instead
  of key presence. Previously, missing CPU and RAM values were treated as 0 %
  load, so they never lowered the hardware score and no repair was shown.
- **No PSI and only one field empty (#123):** same repair and no setup.
  Previously, the missing value was treated as 0 % load.
- **Repairs now affect the application score (#97):** every open repair costs
  5 points, capped at 10, and the application score is hard-capped at 99 while
  any repair is open. Repairs raised by HAGHS itself are excluded.
- **Unregistered entities are informational only (#98):** entities without an
  entity-registry entry no longer count as zombies, no longer lower the score
  and are reported separately (`unregistered_count`, `unregistered_entities`).
  Application Scores can increase after upgrading; details in the Bug Fixes
  section.
- **Zombie grace default shortened to 5 minutes:** zombies are now detected
  after 5 minutes instead of 15. The new default also applies to existing
  installations that never configured a custom value, so scores can drop
  earlier than before. Setting the zombie grace period to 15 minutes in the
  integration options restores the old behaviour.

## Features

### Dead devices are flagged (#120)

**Change:** A device whose entities are **all** `unavailable`/`unknown` beyond the
zombie grace window is reported: `dead_device_count`, `dead_devices` (device names,
capped at 100) and the `rec_dead_devices` flag. New recommendation template:
`🔌 Devices: {count} device(s) with all entities unavailable.`

**No score change:** the marker is informational. The entity-level zombie points
stay authoritative, so the same entities are not penalised twice.

**Exclusions:** `ignore_labels` and `ignore_patterns` mute devices exactly like for
zombies (device label, entity labels, entity-id patterns). Devices without entities
are not part of this feature (that is the "empty devices" idea from #93, out of
scope).

**Files changed:**
- `custom_components/haghs/const.py` - `REC_DEAD_DEVICES`, `REC_TEMPLATES` entry,
  `DEAD_DEVICE_LIST_CAP`, `rec_dead_devices` flag key
- `custom_components/haghs/coordinator.py` - `_past_grace()` (shared grace helper),
  `_calc_dead_devices()`, new result attributes and flag
- `custom_components/haghs/sensor.py` - `dead_device_count`, `dead_devices`
  attributes
- `custom_components/haghs/strings.json` and
  `custom_components/haghs/translations/en.json` - `rec_dead_devices` (1:1)
- `tests/test_dead_devices.py` (new) - detection, grace, exclusions, no double

- `README.md` - Dead Devices bullet and attribute table

### Recommendation texts are translatable (#114)

**Change:** The 18 recommendation templates (`REC_*` in `const.py`) are resolved at
runtime for the configured HA language via Home Assistant's translation system
(category `common` in `strings.json` / `translations/en.json`). English is the
fallback, then the `const.py` default, so a missing key can never produce an empty
recommendation.

**No behavior change:** for English users the rendered strings stay byte-identical
(guarded by a test that mirrors `translations/en.json` against `const.py`). No score
change.

**Deviation from the issue:** the issue proposed a custom translation category.
hassfest rejects custom top-level categories (`extra keys not allowed`), so the
templates live in the schema-valid `common` category.

**Files changed:**
- `custom_components/haghs/const.py` - `REC_TEMPLATES` mapping, comment updates
- `custom_components/haghs/coordinator.py` - `_async_load_rec_translations()`,
  `_rec()`, the recommendations builder, both result paths
- `custom_components/haghs/strings.json` and
  `custom_components/haghs/translations/en.json` - `common` category (1:1)
- `tests/test_recommendations_i18n.py` (new) - mirror test, fallback chain,
  override, error path, update cycle
- `README.md` - the recommendation texts are translatable

### Repairs now affect the application score (#97)

**Change:** Open repair issues from HA's issue registry cost **5 points each**,
capped at **10 points**. While any repair is open, the application score is
**hard-capped at 99**, so the Config-Audit bonus can never mask a broken
integration. Counted are only issues that are active, not dismissed via HA's
native "Ignore" action and owned by another integration; repairs raised by
HAGHS itself are excluded (they describe the integration's own prerequisites).

**Score change:** this affects existing installations. An instance with open
repair issues scores lower than before, by design. The new attributes are
`repair_count` and `repairs` (`domain/issue_id` list), the new flag is
`rec_repairs`.

**Opt-out:** HA's native "Ignore" action on a repair (Settings > Repairs)
removes it from the count. No new HAGHS option is needed.

**Known overlap:** a broken backend often raises a repair issue *and* leaves
its config entry unhealthy, so one root cause can cost up to 25 points
together (15 for integration health, 10 for repairs). The caps keep that
double signal bounded.

**Files changed:**
- `custom_components/haghs/const.py` - `REPAIR_PENALTY_PER_ISSUE`,
  `REPAIR_PENALTY_CAP`, `REPAIR_LIST_CAP`, `REC_REPAIRS`, new flag key
- `custom_components/haghs/coordinator.py` - `_calc_repairs()`, the new
  `_ApplicationResult` fields, the new formula term, the extended hard cap,
  the recommendation branch and the flag
- `custom_components/haghs/sensor.py` - two new state attributes
- `tests/test_repairs_pillar.py` (new) - counting, caps, dismissal, own
  domain, score effect and the failure path
- `tests/test_score_explainability.py` - the invariant now covers repairs too
- `README.md` - pillar list, attribute table, flag table

## Bug Fixes

### Options and recommendation texts corrected

**Problem:** Three user-facing texts had drifted from the code: the zombie
grace option description still named 15 minutes as the default (actual
default: 5), the ignore-pattern description did not mention that pattern
matches are also excluded from the unregistered listing, and the core-lag
recommendation said ">3 months" while the check triggers at 3 months or more.

**Fix:** `strings.json` and `translations/en.json` now match the code (both
files mirrored 1:1), and the `rec_core_lag` template uses the same threshold
wording in the translations and in the `const.py` fallback. The unused
`ATTR_NONE` constant was removed.

**No behavior change:** text-only, no score effect.

**Files changed:**
- `custom_components/haghs/strings.json` and
  `custom_components/haghs/translations/en.json` - wording fixes (1:1)
- `custom_components/haghs/const.py` - `REC_CORE_LAG` wording, unused
  `ATTR_NONE` removed

### Every missing score point is now explained (#92)

**Problem:** Two point sources were invisible: the Config-Audit bonus (+10 for
recorder purge days / entity filter) and the Integration Health penalty (5 pts
per unhealthy integration). A score well below 100 could therefore have no
explanation in the `recommendations` attribute at all, and no `rec_*` flag
pointed at the missing points.

**Fix:** Both sources now produce a recommendation line and a `rec_*` flag, and
two new attributes expose the raw numbers: `integration_unhealthy_count`
(number of config entries in SETUP_ERROR / SETUP_RETRY / FAILED_UNLOAD) and
`config_audit_bonus` (earned bonus points, 0-10). The new flags are
`rec_integration_health` and `rec_config_audit`, the latter meaning "bonus
points are missing", not "your configuration is bad". A new test
(`tests/test_score_explainability.py`) turns this into an invariant: no missing
point without a text and a flag.

**No score change:** the formula is untouched, every instance keeps the same
score values for a given state. Only the explanation grows.

**Files changed:**
- `custom_components/haghs/const.py` - `REC_INTEGRATION_HEALTH`,
  `REC_CONFIG_AUDIT`, `CONFIG_AUDIT_MAX_BONUS`, two new flag keys
- `custom_components/haghs/coordinator.py` - `_count_unhealthy_integrations()`,
  the new `_ApplicationResult` field, two recommendation branches, two flags,
  two result keys in both `_build_result` and `_neutral_result`
- `custom_components/haghs/sensor.py` - two new state attributes
- `tests/test_score_explainability.py` (new) - the invariant test
- `tests/test_recommendations.py`, `tests/test_recommendation_branches.py` -
  the all-clear cases now assume the fully earned bonus
- `README.md` - attribute table, flag table and pillar notes

### Coordinator can no longer be killed by an unguarded sub-component (#103)

**Problem:** `_build_recommendations` and `_build_rec_flags` ran outside the
`_safe_calc` safety net. An exception in either of them propagated out of
`_async_update_data`, which can interrupt the Home Assistant Core
`DataUpdateCoordinator` refresh cycle. The sensor then silently stops
updating until a manual integration reload (reported: interval not
applied, updates stalled for hours with no log entries).

**Fix:** `_async_update_data` is now a total safety-net wrapper. Any
exception is logged with a full traceback; the last valid result is
returned so the sensor never loses its value, with a neutral fallback for
the very first update. The previous logic moved to
`_async_update_data_inner`, and the result-dict assembly was extracted
into `_build_result`. The `_neutral_result` fallback builds its dict
inline and never calls the potentially failing sub-components.

**Files changed:**
- `custom_components/haghs/coordinator.py` - total safety net around the
  update cycle, `_build_result` / `_neutral_result` helpers
- `tests/test_coordinator_resilience.py` - three regression tests (red
  before the fix): no-raise on recommendations/rec-flags failure, last
  result kept on failure

### Label service names in the docs and UI text corrected (#99)

**Problem:** The README automation example, the `ignore_labels` field
descriptions in `strings.json` / `translations/en.json` and the `_is_ignored`
docstring in `coordinator.py` referenced the services `label.assign` and
`label.remove`. Those names do not exist in Home Assistant, so users could not
build a working automation from the documented example (reported on HA
2026.7.4).

**Fix:** All references now use the actual service names,
`homeassistant.add_label_to_entity` and
`homeassistant.remove_label_from_entity`. Texts and a docstring only; no
behavior change.

**Files changed:**
- `README.md` - service names in the automation example (comment and call) and
  in the v2.3.0 highlight entry
- `custom_components/haghs/strings.json` + `translations/en.json` -
  `ignore_labels` data description (setup and options)
- `custom_components/haghs/coordinator.py` - `_is_ignored` docstring
- `ROADMAP.md` - multi-label ignore entry in the v2.3 completed list

### Entities without an entity-registry entry no longer count as zombies (#98)

**Problem:** HAGHS classified entities that exist in the state machine but
have no entity-registry entry (YAML-defined templates, Utility Meter,
Riemann Sum integrators, ...) as zombie entities and let them reduce the
Application Score. Those entities are fully operational; a missing registry
entry is a characteristic of how they were created, not an operational
problem. They were also indistinguishable from real zombies in the
`zombie_entities` attribute (surfaced with a `[unregistered]` prefix) and
could not be ignored via labels, because labels require a registry entry.

**Fix:** Unregistered entities are now classified separately and are
informational only. They no longer contribute to `zombie_count`, the ratio
penalty or the hard-cap at 99; the detection itself (grace periods, ignore
labels/patterns, domain filter) is unchanged.

**Behavior change (visible):**
- New state attributes: `unregistered_count`, `unregistered_entities`
  (capped at 100) and `unregistered_count_per_domain`. They never affect
  the score.
- `zombie_count`, `zombie_entities` and `zombie_count_per_domain` no longer
  include unregistered entities, and the `[unregistered]` prefix marker is
  gone (constant `ATTR_UNREGISTERED_PREFIX` removed).
- Application Scores can **increase** on instances where such entities were
  previously counted as zombies. The once-per-entity log message now states
  explicitly that unregistered entities do not affect the score.

**Files changed:**
- `custom_components/haghs/coordinator.py` - `_calc_zombies` returns
  zombies and unregistered entities separately; new `_ApplicationResult`
  fields and result-dict keys
- `custom_components/haghs/const.py` - `ATTR_UNREGISTERED_PREFIX` removed,
  `UNREGISTERED_LIST_CAP` added
- `custom_components/haghs/sensor.py` - three new `unregistered_*` state
  attributes
- `README.md` - zombie pillar description, sensor attribute table and the
  zombie dashboard card example
- `tests/test_zombies.py` - helpers now create registered zombies; the
  unregistered classification is covered by new/rewritten tests
- `tests/test_application.py` - new test proving unregistered entities
  cannot cap the application score

## Tests

### Per-pillar coverage for the hardware and application pillars (#107)

**Problem:** `coordinator.py` was at 69 % and several scoring paths had no
test at all: the disk tiers, the classic CPU/RAM fallback with its clamps,
the integration-health cap, both database size paths, the recorder bonus, the
core-update lag and every `rec_*` flag branch. A future threshold edit could
then change scores without a single test failing.

**Change:** The suite grows from 103 to 211 tests and `coordinator.py`
reaches 100 % statement and branch coverage; the package total moves from
66 % to 87 %. No production code changed.
