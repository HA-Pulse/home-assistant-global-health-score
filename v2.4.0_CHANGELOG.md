# HAGHS v2.4.0 Changelog

All changes on the `dev` branch after the v2.3.0 release. The fixes
previously collected in the v2.3.1 changelog are included here; v2.3.1 was
never released separately.

## Behavior changes

- **Entity lists no longer in recorder history:** on large instances the score
  sensor's recorded attributes could exceed Home Assistant's 16 KB recorder
  limit (measured: 100 zombies, dead devices and unregistered entities with
  80-character ids give 26 KB). Above the limit Home Assistant stores no
  attributes at all for that state and logs a warning, so the history of the
  pillars, counts and flags was lost too. `zombie_entities`,
  `unregistered_entities`, `dead_devices`, `repairs` and `pending_updates` are
  now excluded from recorder history, like `stale_candidates`. Their current
  values, names and shapes are unchanged, so cards and automations keep
  working. The counts, breakdowns, pillars and `rec_*` flags stay in the
  history. A test keeps every list or dict attribute either excluded or on a
  short, reasoned list of small ones.
  Files changed: `custom_components/haghs/sensor.py`,
  `tests/test_recorder_attribute_size.py`,
  `tests/data/recorder_attribute_size_dev.json`, `README.md` and
  `v2.4.0_CHANGELOG.md`.

- **Area ignore labels (discussion #96):** configured ignore labels now also
  exclude entities in their effective Home Assistant area from zombie,
  dead-device, update and stale checks. An entity's own area takes precedence
  over its inherited device area. Direct entity/device labels and entity-ID
  patterns remain independent exclusion rules. Area and label changes apply
  on the next regular evaluation, with no new option or migration. Area labels
  do not opt entities into stale monitoring or exclude integration entries
  from Integration Health. Existing selected labels on areas now take effect
  and can change scores by excluding those entities.
  Files changed: `custom_components/haghs/coordinator.py`,
  `tests/test_ignore_paths.py`, `tests/test_zombies.py`,
  `tests/test_dead_devices.py`, `tests/test_updates.py`,
  `tests/test_stale_entities.py`, `README.md` and `v2.4.0_CHANGELOG.md`.

- **Opt-in stale reporting (discussion #79):** passive candidates use only
  `state.last_reported` for sensor and binary_sensor entities, with a default
  threshold of 24 hours configurable from 1 to 8760 whole hours. Scores are
  unchanged without watch labels. Direct entity watch labels opt in entities
  in any domain; device and area labels do not opt in. Each overdue watched
  entity costs 5 application points, capped at 10 before the configuration
  bonus, with a 99 application-score ceiling while any watch finding remains.
  Ignore rules, disabled entities, own-platform entities and unknown or
  unavailable states are excluded. Both sorted entity-ID lists are capped
  at 100 and excluded from recorder history; counts remain complete and
  recorded. New recommendation and flag explain the raw penalty. Old reports
  are not proof of device failure; restarts can reset report timestamps, and
  historical downtime is not reconstructed. Threshold, opt-in and persistence
  checks use unit tests, not artificially aged live entities. This describes
  development behavior, not a stable release.
  Files changed: `custom_components/haghs/const.py`,
  `custom_components/haghs/config_flow.py`,
  `custom_components/haghs/coordinator.py`, `custom_components/haghs/sensor.py`,
  `custom_components/haghs/strings.json`,
  `custom_components/haghs/translations/en.json`, `tests/test_stale_entities.py`,
  `tests/test_options_flow.py`, `tests/test_application_components.py`,
  `tests/test_coordinator_resilience.py`, `tests/test_pillar_fallback_visibility.py`,
  `tests/test_recommendations_i18n.py`, `tests/test_score_explainability.py`,
  `README.md`, `ROADMAP.md` and `v2.4.0_CHANGELOG.md`.

- **Calculation failures are visible (#135):** failed or timed-out main pillars
  now expose `pillar_fallback_count`, `pillar_fallbacks` (hardware, then
  application) and `rec_pillar_fallback`, with a translated warning instead of
  an all-clear. Neutral fallback data is not treated as a measured missing
  Config-Audit bonus; recommendations for the successful pillar remain intact.
  An outer update failure retains the numeric result in a new dictionary and
  sets `update_cycle_failed` and `rec_update_failed`. The first failed update
  keeps the existing neutral numbers, but warns instead of reporting health.
  Successful refreshes clear the indicators. Cancellation still propagates.
  Score formulas, weights, rounding, penalties, caps and numeric fallback values
  are unchanged. Both unchanged dashboard examples display the new warnings.
  Files changed: `custom_components/haghs/coordinator.py`,
  `custom_components/haghs/sensor.py`, `custom_components/haghs/const.py`,
  `custom_components/haghs/strings.json`,
  `custom_components/haghs/translations/en.json`,
  `tests/test_pillar_fallback_visibility.py`,
  `tests/test_coordinator_resilience.py`, `tests/test_recommendations_i18n.py`,
  `tests/test_pillar_fallback_cards.py`, `README.md`, `v2.4.0_CHANGELOG.md`.

- **Dead-device false positives removed (#143):** a device is now reported only
  when all monitored entities in `ZOMBIE_DOMAINS` are `unavailable` beyond their
  respective grace periods. `unknown` does not count as an outage. Domains
  outside `ZOMBIE_DOMAINS` are excluded in both detection passes, and devices
  without monitored entities are not flagged. Previously, all entity domains
  were considered and `unknown` counted as an outage, causing false device
  warnings for idle entities. Existing ignore rules and grace periods remain
  unchanged. This device warning stays informational: entity-level zombie
  detection and scoring are unchanged. The recommendation and README now
  describe monitored entities explicitly.
  Files changed: `custom_components/haghs/coordinator.py`,
  `custom_components/haghs/const.py`, `custom_components/haghs/strings.json`,
  `custom_components/haghs/translations/en.json`, `tests/test_dead_devices.py`,
  `README.md` and `v2.4.0_CHANGELOG.md`.
- **No PSI and no CPU/RAM fallback sensors (#123):** entries with both fields
  empty now raise the `fallback_missing` repair and do not set up until the
  sensors are configured; the setup gate checks the configured values instead
  of key presence. Previously, missing CPU and RAM values were treated as 0 %
  load, so they never lowered the hardware score and no repair was shown.
- **No PSI and only one field empty (#123):** same repair and no setup.
  Previously, the missing value was treated as 0 % load.
- **Repairs now affect the application score (#97):** every open repair costs
  5 points, capped at 10, and the application score is hard-capped at 99 while
  any repair is open. Repairs raised by HAGHS itself are excluded.
- **Unregistered entities are informational only (#98):** entities without an
  entity-registry entry no longer count as zombies, no longer lower the score
  and are reported separately (`unregistered_count`, `unregistered_entities`).
  Application Scores can increase after upgrading; details in the Bug Fixes
  section.
- **Zombie grace default unchanged:** the default was already 5 minutes in
  v2.3.0. This release does not shorten it or change existing custom values.
  This corrects the earlier release-note claim of a change from 15 minutes;
  detection timing and scores are unchanged by this documentation correction.

## Features

### Empty devices are reported (#93)

Devices without any entity are typical leftovers after removing or re-pairing a
device ("registry cruft", #93). HAGHS now reports them, using Home Assistant
facts only: no entity in the entity registry (disabled entities included), the
device is not disabled and not a service entry, no other device is connected
through it (`via_device_id`, so hubs and bridges are skipped), and its config
entry is loaded. Ignore labels on the device or its area mute it, and nothing is
reported before the zombie grace period has passed after a restart. New
attributes `empty_device_count` and `empty_devices` (names, sorted, capped at
100, excluded from recorder history), flag `rec_empty_devices` and the
recommendation `🗂️ Devices: {count} device(s) without any entity.` (also in
pt-BR and German). Both dashboard cards show the count, the Pro card lists the
names. Informational only: score, penalties and every existing attribute are
unchanged. Duplicate detection by `_2` / `_3` suffixes (the first idea in #93)
is not part of this: it would be a rule based on names.

### Why each zombie is reported (#154)

Two new sensor attributes give every zombie one reason, taken only from facts
Home Assistant itself keeps, first match in a fixed order:
`config_entry_missing` (the entity's config entry no longer exists),
`integration_not_loaded` (the entry exists but is not loaded), `not_provided`
(HA only restored the stored state because no running integration provides
the entity) and `unavailable` (the integration runs and reports the entity as
unavailable/unknown). `zombie_count_per_reason` holds the full counts in that
order; `zombie_reasons` names the reason per entry of `zombie_entities` (same
100 entries) and is excluded from recorder history. Only
`config_entry_missing` is a strong hint of an orphaned entity; the other
reasons are no reason to delete. Informational only: score, penalties, flags,
recommendations and every existing attribute are unchanged (pinned by a test).

### Repairs now affect the application score (#97)

**Change:** Open repair issues from HA's issue registry cost **5 points each**,
capped at **10 points**. While any repair is open, the application score is
**hard-capped at 99**, so the Config-Audit bonus can never mask a broken
integration. Counted are only issues that are active, not dismissed via HA's
native "Ignore" action and owned by another integration; repairs raised by
HAGHS itself are excluded (they describe the integration's own prerequisites).

**Score change:** this affects existing installations. An instance with open
repair issues scores lower than before, by design. The new attributes are
`repair_count` and `repairs` (`domain/issue_id` list), the new flag is
`rec_repairs`.

**Opt-out:** HA's native "Ignore" action on a repair (Settings > Repairs)
removes it from the count. No new HAGHS option is needed.

**Known overlap:** a broken backend often raises a repair issue *and* leaves
its config entry unhealthy, so one root cause can cost up to 25 points
together (15 for integration health, 10 for repairs). The caps keep that
double signal bounded.

## Bug Fixes

### Integration Health names config entries, not integrations

The Integration Health count is the number of config entries in `SETUP_ERROR`,
`SETUP_RETRY` or `FAILED_UNLOAD`, so one integration with two failing entries
counts 2, while the integrations page shows one integration. A beta tester saw 4
reported against 3 integrations. The recommendation now says
`🧩 Integrations: {count} integration entry(ies) failed to set up.` instead of
`... {count} integration(s) failed to set up.`, the pt-BR text names
"entrada(s) de integração", and both dashboard cards and the
`rec_integration_health` attribute row say "integration entry/entries". Count,
penalty, flag and score are unchanged.

### Every missing score point is now explained (#92)

**Problem:** Two point sources were invisible: the Config-Audit bonus (+10 for
recorder purge days / entity filter) and the Integration Health penalty (5 pts
per unhealthy integration). A score well below 100 could therefore have no
explanation in the `recommendations` attribute at all, and no `rec_*` flag
pointed at the missing points.

**Fix:** Both sources now produce a recommendation line and a `rec_*` flag, and
two new attributes expose the raw numbers: `integration_unhealthy_count`
(number of config entries in SETUP_ERROR / SETUP_RETRY / FAILED_UNLOAD) and
`config_audit_bonus` (earned bonus points, 0-10). The new flags are
`rec_integration_health` and `rec_config_audit`, the latter meaning "bonus
points are missing", not "your configuration is bad". A new test
(`tests/test_score_explainability.py`) turns this into an invariant: no missing
point without a text and a flag.

**No score change:** the formula is untouched, every instance keeps the same
score values for a given state. Only the explanation grows.

### Coordinator can no longer be killed by an unguarded sub-component (#103)

**Problem:** `_build_recommendations` and `_build_rec_flags` ran outside the
`_safe_calc` safety net. An exception in either of them propagated out of
`_async_update_data`, which can interrupt the Home Assistant Core
`DataUpdateCoordinator` refresh cycle. The sensor then silently stops
updating until a manual integration reload (reported: interval not
applied, updates stalled for hours with no log entries).

**Fix:** `_async_update_data` is now a total safety-net wrapper. Any
exception is logged with a full traceback; the last valid result is
returned so the sensor never loses its value, with a neutral fallback for
the very first update. The previous logic moved to
`_async_update_data_inner`, and the result-dict assembly was extracted
into `_build_result`. The `_neutral_result` fallback builds its dict
inline and never calls the potentially failing sub-components.

**Files changed:**
- `custom_components/haghs/coordinator.py` - total safety net around the
  update cycle, `_build_result` / `_neutral_result` helpers
- `tests/test_coordinator_resilience.py` - three regression tests (red
  before the fix): no-raise on recommendations/rec-flags failure, last
  result kept on failure

### Label service names in the docs and UI text corrected (#99)

**Problem:** The README automation example, the `ignore_labels` field
descriptions in `strings.json` / `translations/en.json` and the `_is_ignored`

### Entities without an entity-registry entry no longer count as zombies (#98)

**Problem:** HAGHS classified entities that exist in the state machine but
have no entity-registry entry (YAML-defined templates, Utility Meter,
Riemann Sum integrators, ...) as zombie entities and let them reduce the
Application Score. Those entities are fully operational; a missing registry
entry is a characteristic of how they were created, not an operational
problem. They were also indistinguishable from real zombies in the
`zombie_entities` attribute (surfaced with a `[unregistered]` prefix) and
could not be ignored via labels, because labels require a registry entry.

**Fix:** Unregistered entities are now classified separately and are
informational only. They no longer contribute to `zombie_count`, the ratio
penalty or the hard-cap at 99; the detection itself (grace periods, ignore
labels/patterns, domain filter) is unchanged.

**Behavior change (visible):**
- New state attributes: `unregistered_count`, `unregistered_entities`
  (capped at 100) and `unregistered_count_per_domain`. They never affect
  the score.
- `zombie_count`, `zombie_entities` and `zombie_count_per_domain` no longer
  include unregistered entities, and the `[unregistered]` prefix marker is
  gone (constant `ATTR_UNREGISTERED_PREFIX` removed).
- Application Scores can **increase** on instances where such entities were
  previously counted as zombies. The once-per-entity log message now states
  explicitly that unregistered entities do not affect the score.

- `custom_components/haghs/coordinator.py` - `_calc_zombies` returns

- `custom_components/haghs/const.py` - `ATTR_UNREGISTERED_PREFIX` removed,
