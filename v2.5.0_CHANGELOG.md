# HAGHS v2.5.0 Changelog

All changes on the `dev` branch after the v2.4.2 release.

## Unreleased

### HAGHS's own repairs never stop the update; several entries keep separate state (#217)

- **A failing repair no longer stops the update.** HAGHS keeps its "CPU and
  RAM are not measured" repair in step in every update. If Home Assistant's
  issue registry fails there, HAGHS now logs one warning per failure streak,
  calculates score and attributes as usual and tries again in the next
  update; before, the whole update failed and the last result stayed. The
  same applies to the repair about unreadable stored update times.
- **Several HAGHS entries no longer interfere.** Each entry has its own
  repairs (`fallback_missing_<entry id>`, `update_first_seen_unreadable_<entry
  id>`) and its own record of when pending updates were first seen (stored as
  `haghs.update_first_seen.<entry id>`). Before, one entry could remove the
  other entry's repair, and an ignore label in one entry restarted the 7-day
  update grace of the other.
- **Updating keeps every running 7-day window.** When an existing entry is
  updated (config entry version 3.5), HAGHS copies the shared store of HAGHS
  2.4 into the entry's own store once; the old file stays untouched, and
  entries added later start empty. If the old file cannot be read, HAGHS
  warns and raises its "could not read its stored update times" repair. An
  old shared CPU/RAM repair is replaced by the entry's own. Removing a HAGHS
  entry removes its repairs.

No change to scores, attributes or repair texts. Files changed:
`custom_components/haghs/__init__.py`, `const.py`, `coordinator.py`,
`repairs.py`, `tests/factories.py`, `tests/test_repair_sync_guarded.py`,
`tests/test_entries_separate_state.py`, `tests/test_repairs_pillar.py`,
`tests/test_repair_optional_sensors.py`, `tests/test_setup_fallback.py`,
`tests/test_cpu_ram_source_update.py`, `tests/test_update_first_seen_unreadable.py`,
`tests/test_update_grace_restart.py`, `tests/test_update_grace_restart_pins.py`,
`tests/test_updates.py`, `tests/test_child_devices_ignore.py`,
`v2.5.0_CHANGELOG.md`.

### Full support for child devices (#219)

Home Assistant 2026.11 can split a device into child devices, one per part
(for example each socket of a power strip). HAGHS now treats them as devices
of their own:

- **Empty child devices are reported.** A child device without any entity is
  listed in `empty_devices` / `empty_device_ids` and counted in
  `empty_device_count`, under the same rules as other devices (not disabled,
  config entry loaded, not ignored); a child of a disabled parent is skipped.
  The parent itself is still never reported. Informational, no score impact.
- **Dead child devices** were already reported by their own name; tests now
  cover it.
- **Behavior change: an ignore label on a parent device covers its child
  devices.** Entities on the child devices are excluded from zombie
  detection, update penalties, stale watch labels and the dead and empty
  device checks, exactly like entities on the labeled device itself. Example:
  a power strip labeled `haghs_ignore` with a socket child device whose switch
  has been unavailable for an hour: before, the switch counted as a zombie and
  could cost points; now it is ignored, so the score can rise. Labels on the
  parent's area already applied to child entities through Home Assistant's
  area inheritance.

Home Assistant 2026.6 to 2026.10 has no child devices; nothing changes there.
Files changed: `custom_components/haghs/coordinator.py`,
`tests/test_child_devices_empty.py`, `tests/test_child_devices_ignore.py`,
`tests/test_empty_devices_child_parents.py`, `docs/scoring.md`,
`docs/attributes.md`, `script/docs_attributes.py`, `docs/faq.md`,
`docs/configuration.md`, `v2.5.0_CHANGELOG.md`.

### No warning about child devices' `via_device_id` (#214)

Since Home Assistant 2026.11, HAGHS logged "accesses ChildDeviceEntry.via_device_id,
which does not exist on child devices" once after every restart; the access would
stop working in Home Assistant 2027.9.0. The empty-device check now reads child
devices only through their `parent_device_id`, as Home Assistant intends; a child
device never has a via device, so the result is unchanged. No change to scores or
attributes. Files changed: `custom_components/haghs/coordinator.py`,
`tests/test_child_device_via_warning.py`,
`tests/test_empty_devices_child_parents.py`, `v2.5.0_CHANGELOG.md`.

### Code cleanup from SonarCloud findings

The config and options flow build their form with `_flow_schema()`, which
takes no PSI parameter any more: since 2.4 the form is the same with and
without PSI, and the flow step decides whether System Monitor's sensors are
suggested. The docstring now says so. One test patches the PSI read with
`return_value` instead of a lambda, and two code comments no longer name

`custom_components/haghs/config_flow.py`, `coordinator.py`, `repairs.py`,
`tests/test_cpu_ram_source_update.py`, `v2.5.0_CHANGELOG.md`.

### Minimum Home Assistant 2026.6.0, tested in CI (#237)

Behavior change for installation and updates. HAGHS now needs Home Assistant
2026.6.0 or newer (`hacs.json`; before: 2024.10.0). Installations on an older
Home Assistant stay on HAGHS 2.4.2: HACS does not offer this version there, and
the installed version keeps working. The test suite now runs on the current
Home Assistant and on 2026.6.0 (`requirements_test_min.txt`, used by a separate
CI job); tests that need child devices (Home Assistant 2026.11) are skipped on
2026.6 with that reason. No change to scores or attributes. Files changed:
`hacs.json`, `requirements_test_min.txt`, `docs/cards.md`, `tests/conftest.py`,
`tests/factories.py`, `tests/test_min_ha_version.py`, `tests/test_empty_devices.py`,
`tests/test_empty_devices_child_parents.py`, `tests/test_recorder_attribute_size.py`,
`tests/test_repairs_fix_flow.py`, `tests/test_update_first_seen_unreadable.py`,
`tests/test_zombie_reasons.py`, `tests/test_zombie_reasons_recorder.py`,
`tests/test_zombie_since.py`, `v2.5.0_CHANGELOG.md`.

### psutil declared in the manifest (#238)

`manifest.json` lists `psutil>=5.9.0` as a requirement. HAGHS uses psutil for
disk usage; Home Assistant already installs psutil, so nothing is installed or
changed. Only a lower bound is given, never an exact version, so the psutil
version Home Assistant's own integrations use stays as it is. Files changed:
`custom_components/haghs/manifest.json`, `tests/test_manifest_requirements.py`,
`v2.5.0_CHANGELOG.md`.

### Recorder read through Home Assistant's helper (#236)

The config audit reads the recorder settings (keep days, entity filter)
through `homeassistant.helpers.recorder.get_instance()` instead of an internal
`hass.data` key. Without a recorder the audit behaves as before (no recorder
bonus) and logs one debug line. No change to scores or attributes. Files
changed: `custom_components/haghs/coordinator.py`,
`tests/test_recorder_get_instance.py`, `v2.5.0_CHANGELOG.md`.

### Repair confirmation never fails; type findings cleared

A HAGHS repair whose id this version does not know (for example one left by
another HAGHS version) can now always be confirmed and removed; before, opening
it failed. The "CPU and RAM are not measured" repair without stored entry data
now ends with "The HAGHS configuration entry no longer exists." instead of an
error. Type hints in the integration code are corrected so pyright (with the
project settings) reports no errors; six checks that do not fit Home Assistant's
types are ignored line by line with the rule name and a reason. No change to
scores, attributes or options. Files changed: `custom_components/haghs/repairs.py`,
`coordinator.py`, `config_flow.py`, `sensor.py`, `tests/test_repairs_fix_flow.py`,
`v2.5.0_CHANGELOG.md`.

### Developer tooling: pyright settings

`pyproject.toml` gets a `[tool.pyright]` section (Python 3.12 as Ruff's

### An unreadable update-times store stays visible

Behavior change. If HAGHS cannot read the stored times when it first saw each
pending update (for example a file it has no permission to read, or a file
written by a newer HAGHS version after a downgrade), it no longer only writes
a debug line. It keeps a copy of the file next to it
(`.storage/haghs.update_first_seen.unreadable.<UTC time>`), logs one warning
with the traceback, and raises a HAGHS repair "HAGHS could not read its stored
update times" that names the copy; confirming the repair removes it. As
before, pending updates then count from that moment, so for up to 7 days they
do not lower the score. If no copy can be kept, the repair says so and HAGHS
does not save the file in that Home Assistant run, so it is never overwritten;
the warning then names why the copy failed, with the traceback of the copy
error and of the read error. The repair is HAGHS's own and does not count in the score. A file with broken
JSON is still handled by Home Assistant itself (it keeps a `.corrupt` copy and
raises its own repair). Files changed: `custom_components/haghs/const.py`,
`coordinator.py`, `repairs.py`, `strings.json`, `translations/en.json`,
`de.json`, `pt-BR.json`, `docs/faq.md`, `tests/test_update_grace_restart.py`,
`tests/test_update_first_seen_unreadable.py`, `v2.5.0_CHANGELOG.md`.

### Japanese translation (#224)

`translations/ja.json` translates every string of `translations/en.json` into
Japanese, with the same keys and placeholders as English. Other languages keep
English as the fallback. No code or score change. Files changed:
`custom_components/haghs/translations/ja.json`, `docs/scoring.md`,
`v2.5.0_CHANGELOG.md`.
